# IAX11 独显亮度模式定位

当前应优先向 NVIDIA 定位和反馈，工程判断置信度约85%。本机 EDO EF25QBA63.E 在 Linux 独显默认相对DPCD调光路径下亮度偏低；启用面板绝对亮度控制并指定250尼特目标值后，用户确认亮度正常。用户进一步确认同机 Windows 独显直连亮度正常。Windows 的 HDR 状态尚待确认，当前还没有 Windows 寄存器快照。

这一判断指向 NVIDIA Linux 的调光模式选择、范围换算或 GSP 与 OEM 配置的配合。确切缺陷是否源自 NVIDIA 算法、联想固件提供的配置，或需要针对 EDO 相对模式做兼容处理，仍需要跨系统控制状态对照。85%是基于本机证据的工程判断，不是统计概率或厂商确认。

## 厂商归属判断

| 对象 | 当前证据与判断 |
| --- | --- |
| NVIDIA | 默认亮度设备由 NVIDIA 注册；0–100百分比直接进入 NVIDIA RM/GSP。Linux 下通过同一 NVIDIA AUX 通道下发绝对亮度可以正常工作。NVIDIA 是首要修复和反馈对象。 |
| 联想 | BIOS GETBACKLIGHT 调用成功、运行时返回与静态表一致，未发现接口缺失或返回损坏。配置语义、初始化时序或针对不同系统的适配仍需核对。 |
| EDO | 同一面板在 Windows 和 Linux 绝对亮度模式下可以正常发亮，现有表现不支持“面板发光能力不足”的解释。相对调光实现是否符合规范，需要具体控制状态和面板规格。 |

Windows 正常说明该硬件组合存在可工作的控制方式。若 Windows 使用绝对亮度、Linux 使用相对亮度，可进一步确认驱动栈的路径差异；若模式相同但参数不同，则继续查范围换算及 OEM 标定。若亮度寄存器相同而表现不同，还需追查初始化状态。跨系统结果可以收窄归属，不能预先当作某一家已被证实存在具体代码缺陷。

## 实机证据

测试期间暂停nv-bright服务，避免后台控制覆盖指令。A与B期间，面板模式、PWM有效位数8、系统滑块及250000毫尼特目标字段保持一致。B只改变相对亮度的高字节。

| 状态 | 模式0x721 | 相对值0x722–0x723 | 绝对目标字段 | 用户观察 |
| --- | --- | --- | --- | --- |
| 测试前 | 0x8a，绝对控制启用 | 0x00ff | 250000毫尼特 | 正常亮度 |
| A，5秒 | 0x0a，绝对控制关闭 | 0x00ff | 250000毫尼特 | 明显变暗 |
| B，8秒 | 0x0a，绝对控制关闭 | 0x40ff | 250000毫尼特 | 与A接近，同样明显变暗 |
| 恢复后 | 0x8a，绝对控制启用 | 0x00ff | 250000毫尼特 | 恢复正常 |

日志确认各阶段寄存器写入及读回成功。恢复过程核对原模式、相对值、目标字段均一致，服务也已恢复active/running。用户确认A、B都明显变暗，结束后正常。

这些结果支持亮度差异与面板控制模式有关。B阶段高字节单字节写入没有带来可见改善；该测试没有覆盖完整双字节写入的行为，因此不能彻底排除提交方式或位对齐的影响。尚未取得本面板关于多字节写入生效时机的规格，不能把这种可能性当作已证实的原因。测试也没有证明原有相对值255就是错误编码，没有测量实际物理尼特值。

## BIOS配置已核对

- 取得本机32张ACPI表，长度与校验和全部通过。
- NVIDIA NBCI方法位于SSDT26，函数0x14 GETBACKLIGHT存在。
- 函数返回32项配置，开头为0x8000a450、0x0203。HDRS两分支返回完全相同内容，该函数内没有按操作系统分流。
- 驱动运行时查询成功，返回128字节，与离线反汇编常量逐字节一致。

因此，本次查询中的BIOS接口缺失、调用失败或返回内容与静态表不一致，均未出现。配置的具体标定语义是否适合此面板，还需要厂商确认。

## NVIDIA代码路径

源码为官方595.99.02，提交 `e394a404108a9ce5bba988c1dddf694dabbd4a43`。

```text
GNOME／亮度键 → nvidia_0（0–100）
→ nvKmsSetBacklight（PERCENT100）
→ RM 0x730292 → GSP固件
→ 面板亮度模式与寄存器
```

Linux入口按接口约定发送0–100百分比。物理亮度处理实现位于GSP固件；公开源码只包含入口、参数和路由。BIOS GETBACKLIGHT配置由驱动初始化代码传给GSP。

三个RM GET亮度查询均返回0x1b，官方状态码为 NV_ERR_INSUFFICIENT_PERMISSIONS。它们返回的零值不能作为亮度读数，也不能用于判断固件内部换算结果。

## 当前处理与定位边界

nv-bright服务已启用并运行，使用5–250尼特范围，系统滑块调节已实测有效。本次启动的boot ID为`0de87c6b-adb3-4349-b015-007fcaf65de7`，服务在2026-10-20 18:06:13 PDT启动，日志确认watch进程运行，已验证开机自启。长期稳定性与休眠恢复仍待观察。

当前有硬件证据支持的处理是使用绝对亮度路径。进一步定位具体缺陷，需要Windows正常状态的DPCD快照，并由NVIDIA解释GSP如何消费本机0x0203配置。联想和EDO的配置／面板规格可用于核对该处理是否正确。

## Windows对照采集已备好

`windows-snapshot.zip`包含一个只读采集入口和未修改的`cnbright/gpu_aux`源代码，固定提交`eda49e230b48a7a8b995b664a8a0756b2bde99f1`，随附MIT许可。它使用现有Windows x64 Python和系统`nvapi64.dll`，读取DPCD能力、控制模式、相对亮度、PWM有效位数与绝对目标字段，并采集Windows CIM面板信息。运行步骤见包内`使用说明.md`。

采集脚本与原后端已通过模拟NVAPI DLL的4种实际入口验证：正常读取、接口拒绝、没有端口、未取得管理员权限。验证确认原生AUX命令仅为read，错误结果不会被解码为有效亮度。Windows实机兼容性待验证；私有AUX接口可能被特定驱动拒绝。
